# HIX v2.1.03

**Fecha:** 2026-09-09
**Base:** `955e59b` (2.1.02)

## Qué se ha conseguido

Se cierra el segundo agujero del ciclo SSE: en v2.1.02 el patrón `lAlive`
apoyado en el retorno de `USendChunk` era **suficiente para `RST` agresivo
pero no para el `FIN` limpio del navegador** — Windows deja los 4 bytes
de un probe SSE (`":k\r\n\r\n"`) en el buffer TCP local y `send()`
devuelve OK, así que un `Ctrl+F5` en `/sse-test` acumulaba usuarios en
`sse_liveroom_users` porque el worker antiguo seguía vivo mientras el
nuevo ya había incrementado el contador.

La solución es hacer un **`recv MSG_PEEK` con timeout 0** sobre el mismo
socket antes de cada probe. Es una operación no destructiva que detecta
el `FIN` del peer en el mismo tick de 300 ms, sin depender del buffer TCP
ni del kernel keepalive (cuyo primer probe en Windows por defecto es
~2 h — inservible para SSE).

## Cambios

### 1. Nuevo `METHOD PeerAlive()` en `THixIO`

Añadido en `src/hix_io.prg`. Hace `hb_socketRecv(..., 1, HB_SOCKET_MSG_PEEK, 0)`
sobre el socket TCP y clasifica el retorno:

| `hb_socketRecv` | Estado                                      |
|-----------------|---------------------------------------------|
| `0`             | Peer envió FIN → `.F.`                      |
| `> 0`           | Datos peekables → `.T.`                     |
| `-1` + fatal    | CONNRESET/CONNABORTED/NOTCONN/PIPE/SHUTDOWN → `.F.` |
| `-1` + otro     | WOULDBLOCK/AGAIN/etc. → `.T.`               |

Sobre sesiones SSL degrada a `.T.` (el peek TCP no ve los bytes descifrados
del stream). Es limitación conocida — para HTTPS SSE se sigue confiando
en el retorno de `USendChunk` con `hb_idleSleep(0.3)`.

Helper interno `_HixIsFatalSocketError( nErr )` centraliza la
clasificación de códigos de error de socket.

### 2. Wrapper `METHOD PeerAlive() INLINE ::oIO:PeerAlive()` en `THixRequest`

Añadido en `src/hix_request.prg` con NIL-guard sobre `::oIO`. Un request
sin canal de IO (mocks, request abortado, etc.) devuelve `.F.`.

### 3. Nuevo helper `UPeerAlive()` en `hix_helpers.prg`

Delega en `HIX_GetRequest():PeerAlive()`. Devuelve `.F.` si no hay request
activo en el hilo. Uso canónico en handlers de stream:

```harbour
DO WHILE lAlive
   IF ! UPeerAlive()           // primary exit: FIN detectado en el mismo tick
      lAlive := .F.
      LOOP
   ENDIF
   IF ! USendChunk( ... )      // secondary: RST agresivo
      lAlive := .F.
      LOOP
   ENDIF
   ...
ENDDO
```

### 4. Ejemplo `examples/web/hi/www/controllers/api_sse_ticker.prg`

Reescrito con `UPeerAlive()` como salida principal + `USendChunk` como red
de seguridad. Sleep en tramos de 300 ms con peek entre cada uno, para que
un cierre durante la espera se note en <1 s sin depender del `send()`.

## Test de regresión

`tests/unit/src/hix_test_peer_alive.prg` (grupo Transport, entrada
`PeerAlive`) — 6 asserts:

1. `UPeerAlive()` sin request activo → `.F.`
2. `UPeerAlive()` con request pero sin `oIO` → `.F.`
3. `UPeerAlive()` con IO alive → `.T.`
4. `UPeerAlive()` con IO dead → `.F.`
5. Bucle `lAlive` sale después de 3 ticks cuando el peer muere.
6. `THixIO:PeerAlive()` con `hSocket` NIL → `.F.` (guardia).

## Fix adicional — carrera del detector SSE

Con `UPeerAlive()` ya funcionando, apareció un segundo síntoma: el 2º
Start consecutivo de un long-job SSE colgaba (Chrome dispara `onopen`,
ningún chunk llega, `dbg.log` y `access.log` sin traza del request).

**Causa**: `HIX_DetectProtocol` en `src/hix_socket.prg` clasificaba como
legacy pub/sub SSE cualquier peek que contuviera `text/event-stream`, y
el accept loop dispatcha directamente al `oPoolOtros` (worker legacy
`_HixWorkerSSE`) sin pasar por el router. El peek es una carrera:

- Runs que la pierden (peek atrapa solo `GET /...\r\n`): fall through a
  `HIX_CONN_HTTP` → router → controller. OK.
- Runs que la ganan (paquete con cabeceras completas, típico tras una
  reapertura de socket con Happy Eyeballs IPv4 fallback): dispatch al
  worker legacy → 124 bytes de cabeceras hardcodeadas + bucle keep-alive
  del bus por canal. El controller nunca se invoca.

**Fix**: eliminada la línea `IF HIX_TOKEN_SSE_ACCEPT $ cLower ...` de
`HIX_DetectProtocol`. En v2.x todo SSE va por ruta con `stream: true`;
la detección por Accept-header era residual de v1 y solo reintroducía
la carrera. LongPoll conserva su detección.

**Impacto en API**: cero. Rutas ya declaradas con `stream: true` siguen
funcionando idénticas; lo que cambia es que ahora **siempre** llegan al
router (antes era intermitente).

## Impacto

- `HIX_SUBVERSION_SERVER` sube a `.03`.
- API 100% aditiva: `PeerAlive` en `THixIO`/`THixRequest` + helper
  `UPeerAlive` son nuevos. Nada existente cambia de firma ni de retorno.
- Detector SSE: cambio interno no observable por rutas correctamente
  declaradas con `stream: true`. Sí rompe cualquier uso legacy que
  dependiera del dispatch por Accept-header hacia `_HixWorkerSSE`
  (pub/sub por canal sin ruta). Ningún ejemplo en repo depende de eso.
- SSL: `PeerAlive()` devuelve `.T.` (degradado). Documentado.
- Fuera de alcance:
  - **Peek SSL/TLS**: requiere BIO peek o guardar byte descifrado aparte.
    Plan separado (`plan_ssl_peer_alive.md` — futuro).
  - **Tuning `WSAIoctl SIO_KEEPALIVE_VALS`** para acortar el primer
    probe keepalive en Windows (2 h → 30 s).
  - **`AddRouteWs` para unificar WS bajo el router**. Idea documentada
    en `.claude/plans/2026-09-11_0910 v3_addroutews_unified_router.md`.
