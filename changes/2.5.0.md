# HIX v2.5.0

**Date:** 2026-11-19 (PG prepared) · 2026-11-21 (SQLite3/SQLCipher)
**Base:** v2.4.9
**Plans:**
- `.claude/plans/2026-11-18_1937 wdo_pg_prepared_statements.md`
- `.claude/plans/2026-11-19_... wdo_sqlite3_sqlcipher.md` (Camino B)

**Type:** Feature — Completar la familia WDO: prepared statements PG +
driver nativo SQLite3/SQLCipher.

## TL;DR

**`WDO_PG`** estrena **prepared statements nativos** vía `libpq`
(`PQprepare` + `PQexecPrepared`). API 1:1 con `WDO_MySql`:
`Prepare / BindParam / BindParams / BindLong / Execute / Fetch /
Fetch_Assoc / FetchAll / Free`. Tres dialectos de placeholder
(`?`, `:name`, `$N`), SQL injection safe, plan reusable server-side.

**`WDO_Sqlite3`** reescrito como driver **nativo hb_DynCall** sobre
`sqlcipher.dll` (MinGW64 + OpenSSL 4). Sustituye el stub `hbsqlit3`.
Añade **SQLCipher** transparente: `key` / `key_ref` activan cifrado
AES-256-CBC + HMAC-SHA512 por página. Misma superficie que PG/MySQL
(Query, Prepare, Transaction, DbStruct) + API de cifrado
(`Rekey`, `GetCipherInfo`, `IsEncrypted`).

Suites: PG **126 → 142 PASS** · SQLite3 **31 → 47 PASS**.

## Por qué v2.5.0 (y no 2.4.10)

- Nueva API pública en `WDO_PG` — alinea la superficie con `WDO_MySql`
  y `WDO_Sqlite3`. Semver: adición de funcionalidad backward-compatible
  justifica bump de minor.
- Cambio de contrato sutil pero no breaking: `WDO_PgStmt` gana siete
  nuevos DATA (`lPrepared`, `cStmtName`, `cSqlOriginal`, `cSqlServer`,
  `nParamCount`, `aParams`, `hParamMap`) y cuatro métodos
  (`BindParam`, `BindParams`, `BindLong`, `Execute`).
- Se consolidan los tres drivers WDO en la misma superficie: cualquier
  controller puede cambiar `WDO_Get("MYSQL")` por `WDO_Get("PG")` sin
  tocar el flujo Prepare/Bind/Execute.

## API nueva — `WDO_PG`

```harbour
LOCAL oConn := WDO_Get( "PG" )
LOCAL oStmt

//  Tres dialectos de placeholder soportados
oStmt := oConn:Prepare( "SELECT id FROM users WHERE name = ? AND age > ?" )
oStmt:BindParams( { "alice", 20 } )
oStmt:Execute()
aRows := oStmt:FetchAll( .T. )
oStmt:Free()

oStmt := oConn:Prepare( "SELECT id FROM users WHERE name = :who" )
oStmt:BindParam( ":who", "alice" )
oStmt:Execute()

oStmt := oConn:Prepare( "SELECT $1::int + $2::int" )
oStmt:BindParams( { 10, 20 } )
oStmt:Execute()
```

### Métodos nuevos

| Método | Descripción |
|---|---|
| `oConn:Prepare( cSql ) -> WDO_PgStmt` | `PQprepare` con nombre único por thread. Rewrite `?`/`:name` → `$N`. |
| `oStmt:BindParam( xIdxOrName, xVal [, cType] )` | Bind por índice `nIdx` o nombre `":who"`. `cType` opcional: `i/n/s/d/t/b`. |
| `oStmt:BindParams( aValues )` | Bind masivo. Infer tipo del `ValType`. |
| `oStmt:BindLong( nIdx, cData )` | Alias de `BindParam( nIdx, cData, "s" )` (compat MySQL; no hay chunked protocol en libpq). |
| `oStmt:Execute() -> .T./.F.` | `PQexecPrepared`. Puebla `::hRes`, `::nRows`, `::aFields`. Setea `lError/cError`. |
| `oStmt:Free()` | `PQclear` + `DEALLOCATE <name>` server-side. Reentrante. |

### Fetch — reutiliza el pipeline existente

`Fetch()`, `Fetch_Assoc()` y `FetchAll(lAssoc, aNoEscape)` siguen
funcionando igual que con `Query()`. El `PQresult` que puebla `Execute`
pasa por el mismo lector que `Query`.

### Ciclo de vida

- **Nombre del statement**: `hix_pg_<threadId>_<counter>` — único por
  conexión. El `nStmtSeq` es un contador monotónico `DATA` de la
  conexión; aislamiento por thread lo da el pool.
- **`Free()` emite `DEALLOCATE`**: no se filtran planes server-side entre
  requests. El dispatcher no llama `Free()` automáticamente — hay que
  hacerlo en el handler (`FINALLY` recomendado).
- **Reuse**: `oStmt:Execute()` puede llamarse N veces tras cambiar params
  con `BindParam()`; el plan server queda vivo hasta `Free()`.

### Tipos — inferencia automática

Cuando se omite `cType` en `BindParam`, `_WdoPgInferType()` deduce:

| ValType | cType | Marshalling PG |
|---|---|---|
| `N` (int) | `i` | `hb_NToS( nVal )` |
| `N` (float) | `n` | `Str( nVal )` sin padding |
| `D` | `d` | `YYYY-MM-DD` |
| `T` | `t` | `YYYY-MM-DD HH:MM:SS` |
| `L` | `b` | `t`/`f` |
| `C` o `NIL` | `s` | passthrough (NIL → SQL NULL) |

PG sigue siendo estricto con tipos: para operadores que necesitan
desambiguación (`age > ?` vs `age > $1::int`), añadir el `::int` en el
SQL para forzar inferencia. Todos los tests Phase 2bp usan este patrón.

## `WDO_Sqlite3` / SQLCipher — Camino B

### Por qué reescribir

El shim `hbsqlit3` dejó de ser viable cuando se quiso añadir SQLCipher:
- `hbsqlit3` no expone `sqlite3_key` ni las PRAGMAs de SQLCipher.
- Enlazar estáticamente contra SQLCipher en Harbour obligaría a
  recompilar toda la toolchain con OpenSSL embebido.
- El patrón `hb_DynCall` ya está validado en `WDO_PG` (libpq v2.4.4+)
  y convive limpiamente con el WDO de MySQL.

Se adoptó **Camino B**: workspace paralelo `C:\HIX.PROJECT\hix.sqlite3`
que construye `sqlcipher.dll` con MSYS2 MINGW64 reusando el
`openssl-sdk` 4.x de `hix.postgre`. La DLL resultante (1.7 MB) solo
depende de `libcrypto-4-x64.dll`, `KERNEL32` y `msvcrt` — la misma
superficie runtime que `libpq.dll`.

### API nueva — superficie común con PG/MySQL

```harbour
oConn := WDO_Get( "APP" )

//  Query clásica + prepared idénticas a PG/MySQL
oStmt := oConn:Prepare( "INSERT INTO t(name, qty) VALUES(?, ?)" )
oStmt:BindParams( { "widget", 42 } )
oStmt:Execute()
oStmt:Free()

oConn:Transaction( {|o| o:Exec(...), o:Exec(...) } )
```

### API cifrada — SQLCipher

```harbour
//  Hash config (vía hix.json "databases.APP.key" / "key_ref")
WDO_InitSqlite3Ex( "APP", { ;
   "file"             => "data/app.db", ;
   "key"              => "my-passphrase", ;
   "cipher_kdf_iter"  => 256000 ;
} )

oConn := WDO_Get( "APP" )
hInfo := oConn:GetCipherInfo()       // cipher_version / kdf_iter / ...
oConn:Rekey( "new-passphrase" )      // re-encripta en sitio
oConn:lEncrypted                     // .T.
```

Rekey a `""` no desencripta (limitación SQLCipher — vía soportada:
`ATTACH ... KEY '' + sqlcipher_export`).

### Lecciones de ingeniería (codificadas como memorias)

Durante la reescritura salieron tres trampas de `hb_DynCall` que
quedan documentadas para futuros drivers (WDO_Oracle, WDO_Firebird…):

1. **Punteros OUT requieren `VOID_PTR` + `INIT NIL`**
   (`project_hbdyncall_pointer_init_nil.md`). `LLONG_PTR` sobre un
   `sqlite3*` lo lee como entero truncado → cuelgue silencioso al
   pasar `NULL` al siguiente call.
2. **`::nSysLong` lee `HB_IT_POINTER` como 0** — hay que serializar
   con `WDO_PtrNull()` y el slot `VOID_PTR`
   (`project_hbdyncall_ptr_vs_nSysLong.md`).
3. **Tests de error-paths necesitan `bError := {|oErr| .T.}`** — la
   clase base `WDO` tiene `lShowError INIT .T.` y `SetError()` hace
   `Break()` cuando no hay handler, lo que cuelga procesos standalone
   (`project_wdo_test_berror_handler.md`).

## Fuera de scope v2.5.0 (para v2.6+)

- Fetch binario (equivalente a Phase 2b-bin/2b-fetch de MySQL).
  Resultados vuelven en texto, mismo pipeline que `Query`.
- `BindLong` con envío chunked — `libpq` no tiene protocolo chunked
  para params; `BindLong` existe como alias por paridad con MySQL.
- `PQdescribePrepared` para introspection por el usuario — está
  disponible internamente pero sin método público.
- SQLCipher decrypt-to-plaintext vía helper de alto nivel
  (`ATTACH + sqlcipher_export`) — hoy hay que escribirlo a mano.
- `WDO_Sqlite3` build Linux (MinGW produce la DLL Windows; Linux
  necesita `libsqlcipher.so` desde paquetes distro o build propio).

## Notes

- `oConn:Close()` llama a `PQfinish` — libpq cierra todos los prepared
  stmts automáticamente. Al pool volver la conexión, los stmts preparados
  y no liberados siguen vivos server-side. **Siempre llamar `Free()`** en
  el handler, idealmente en un `FINALLY`.
- Nombre de stmt (`hix_pg_<tid>_<n>`) incluye `threadId` para evitar
  colisiones cuando dos requests concurrentes usan la misma conexión del
  pool secuencialmente (el stmt `_5` de un thread sobreviviría al retorno
  de la conn al pool si otro thread intentara preparar con el mismo
  contador).
- `Transaction()` y `Prepare()` son compatibles — un stmt preparado dentro
  de una transacción se re-ejecuta sobre la misma conexión mientras dure
  el bloque.
