# HIX v2.3.01

**Date:** 2026-09-29
**Base:** `7581dcc` (2.3.00 WDO prepared statements)

## What was achieved

**Feature: declarative WDO pool bootstrap from `www/config.json`.**

Hasta 2.3.00 el arranque de pools era programático: `WDO_InitPoolMySql(...)`
con parámetros posicionales al final del `Main()`, uno por driver.
Aceptable para un pool, ruidoso para varias BDs.

2.3.01 añade una capa declarativa que lee la sección `"databases"` del
`www/config.json` y levanta un pool por entrada. El `Main()` de una app
que use N pools se reduce a:

```harbour
FUNCTION Main()
   LOCAL oSrv := THixServer():New()
   HIX_ConfigAppLoad( "www/config.json" )
   HIX_InitPoolsFromConfig()
   oSrv:Start()
   HIX_EndPoolsFromConfig()
RETU NIL
```

Y el JSON:

```json
{
  "databases": {
    "mysql":     { "driver": "mysql", "host": "...", "pool_size": 5, ... },
    "analytics": { "driver": "mysql", "host": "otra", "pool_size": 2,
                   "dll": "c:/apache24/htdocs/libmariadb64.dll",
                   "berror": "WdoErrorHandler" }
  }
}
```

Cada entrada se registra bajo su clave JSON — `WDO_Get("mysql")` y
`WDO_Get("analytics")` conviven en el mismo proceso. Fully backward-compat:
`WDO_InitPoolMySql(...)` posicional sigue funcionando (ahora es un
wrapper sobre `WDO_InitPoolMySqlEx` que consume hash).

### Nuevas API públicas

- `HIX_InitPoolsFromConfig() → hash { <key> => .T./.F. }` — recorre
  `databases`, dispatcha por `driver`, devuelve outcome por clave.
- `HIX_EndPoolsFromConfig() → NIL` — cierra todos los pools registrados.
- `WDO_InitPoolMySqlEx( cKey, hParams )` — variante hash de
  `WDO_InitPoolMySql`. Reconoce `host`, `user`, `pwd`, `db`, `port`,
  `pool_size`, `timeout_ms`, `ping`, `dll`, `berror` (string) y
  `berror_block` (codeblock, usado internamente por el wrapper posicional).
- `WDO_ListPools() → aKeys` — snapshot de claves registradas.

### Resolución de `berror`

El JSON usa `"berror": "WdoErrorHandler"` (string). Al arranque,
`_WdoResolveBErrorFromName` valida con `hb_isFunction(cName)` antes de
construir el codeblock por macro. Si el símbolo no existe: WARN + pool
arranca sin handler (no aborta). Sin este probe, `&()` construye un
codeblock válido cuya llamada explota luego — silencio letal.

### `dll` desde JSON

Precedencia de resolución (mayor prioridad primero):
1. `hParams["dll"]` — explícito por pool
2. env `WDO_LIB_MYSQL` — full path
3. env `WDO_PATH_MYSQL` + nombre canónico (Windows)
4. default por plataforma

`oConn:DllSource()` reporta el origen (`"override"`, `"WDO_LIB_MYSQL"`,
`"WDO_PATH_MYSQL"`, `"default"`) para diagnóstico.

### Robustness fix: factory exception containment

`WDO_Pool:Init` envuelve `Eval(::bFactory)` en `TRY/CATCH`. Antes,
un DLL mal configurado (ruta no existente) llegaba a
`WDO_MySql:Open` → `SetError` → con `lShowError=.T.` → `Break(oErr)`,
la excepción escapaba de la loop, salía de `Init`, salía de
`InitPoolMySqlEx`, salía de `Main` y llegaba al runtime handler que
lanza un modal de error — que sin consola visible **cuelga el proceso**.
Ahora el slot fallido se registra como tal y la loop continúa.

## Diagnóstico durante el desarrollo

Al añadir el caso "bad dll path" del test, la suite se colgaba sin
output tras el último `EndPoolsFromConfig done`. La causa: `WDO`
tiene `CLASSDATA lShowError INIT .T.`, y `SetError` con
`Valtype(::bError) != 'B'` hace `Break(oErr)`. La factory de
`WDO_Pool:Init` no capturaba nada, la excepción escapaba a
`Main()`, y Harbour lanzaba el modal de "unhandled error" sin
consola visible. Fix estructural en `Pool:Init` (`TRY/CATCH`
sobre el `Eval` de la factory), no en el test — cualquier factory
que muera por error de configuración debe fallar el slot, no el
proceso.

Segundo bug encontrado: `_WdoResolveBErrorFromName` con macro `&()`
no falla en nombres inexistentes — el codeblock se construye OK y
solo explota al invocarse (llenaría `bError` de cada conn con un
handler-bomba). Fix: `hb_isFunction(cName)` antes de la macro.
