# HIX v2.1.05

**Date:** 2026-09-13
**Base:** `8aaba02` (2.1.04)

## What was achieved

Large POST bodies are now delivered intact to `UBody()` / `UFiles()`,
and requests that exceed `HIX_MAX_BODY_SIZE` no longer deadlock the
upstream proxy. The trigger was a real deployment behind **Cloudflare
Tunnel**: uploads > ~1 MB from a desktop browser hung indefinitely
while the same test worked from localhost and from a mobile browser.
Diagnosis pointed to two independent bugs in the socket read path.

## Bugs fixed

### 1. `THixIO:Read()` returned partial data on the first `recv`

`src/hix_io.prg` — `Read( nBytes, nTimeout )` did a **single**
`hb_socketRecv()` and returned whatever the kernel had in the receive
buffer at that instant. TCP is a byte stream, not message-oriented:
for a 5 MB body over WAN, a single `recv` typically returns << `nBytes`.

Observed symptom: `THixRequest:ReadBody()` called `oIO:Read( nRemain )`
once and got ~485 KB out of a declared 5 242 880 bytes. HIX considered
the body complete, responded 200 with `received: 497180`, and left
~4.5 MB of upload bytes queued in the socket. Cloudflare Tunnel
waits for the origin to drain the request body before releasing
the response headers to the client — the browser's `fetch()` hung
forever.

Fix: loop `hb_socketRecv()` until `nBytes` is filled or the peer
closes / a recv times out. `nTimeout` keeps its original semantics
(per-recv budget → stall detector). SSL path (`_HixSSLRead`) is
looped identically.

**Side effect (welcome)**: WebSocket payloads > MTU
(`src/hix_worker_ws.prg:359`) were subject to the same latent
truncation. Now fixed by the same loop.

### 2. Oversized bodies short-circuited without draining

`src/hix_request.prg` — when `Content-Length > HIX_MAX_BODY_SIZE`,
`ReadBody()` returned an empty string immediately without reading
anything from the socket. The subsequent response (200 in
`api_upload.prg`, 413 in `HIX_MwBodyLimit`) went out but the socket
still had `nLen` bytes of upload pending. Same deadlock: Cloudflare
Tunnel held the response until the origin finished consuming the
body — which the origin had already decided not to.

Fix: drain the pending body in 64 KB chunks before responding, and
mark `::lKeepAlive := .F.` so the response carries
`Connection: close`. Applied to both `ReadBody()` and
`_HixMwBodyLimitRun()`.

## Changes in the library

### `THixIO:Read` — accumulator loop

`src/hix_io.prg` — the method now loops both branches (TCP and SSL)
until it has accumulated `nBytes` or exit conditions fire:

```harbour
DO WHILE nGot < nBytes
   IF ::lUseSSL .AND. ::hSSLSession != NIL
      cChunk := _HixSSLRead( ::hSSLSession, ::hSocket, nBytes - nGot, nTimeout, @lErr )
      IF lErr ; ::lConnClosed := .T. ; EXIT ; ENDIF
      IF cChunk == NIL .OR. Len( cChunk ) == 0 ; EXIT ; ENDIF
      cBuf += cChunk
      nGot += Len( cChunk )
   ELSE
      cChunk := Space( nBytes - nGot )
      nRead  := hb_socketRecv( ::hSocket, @cChunk, nBytes - nGot, 0, nTimeout )
      IF nRead <  0 ; ::lConnClosed := .T. ; EXIT ; ENDIF
      IF nRead == 0 ; EXIT ; ENDIF
      cBuf += Left( cChunk, nRead )
      nGot += nRead
   ENDIF
ENDDO

RETURN iif( nGot == 0, NIL, cBuf )
```

Exit reasons: peer closed cleanly (`recv == 0`), transport error /
timeout (`recv < 0`), or SSL error. Returns `NIL` only if nothing
was read (preserves original contract for callers that check for
NIL as "peer dead"); returns a partial string if some bytes made
it in before the stall.

### `THixIO:Drain` — new helper

`src/hix_io.prg` — reads and discards `nBytes` in 64 KB chunks
using the looped `Read()`. Used to consume request bodies we've
decided to reject, so the socket ends the transaction cleanly and
the upstream proxy releases the response to the client.

```harbour
METHOD Drain( nBytes, nTimeout ) CLASS THixIO
   LOCAL nDrained := 0, cChunk, nChunk
   hb_default( @nTimeout, HIX_DEFAULT_READ_TIMEOUT )
   DO WHILE nDrained < nBytes
      nChunk := Min( 65536, nBytes - nDrained )
      cChunk := ::Read( nChunk, nTimeout )
      IF cChunk == NIL .OR. Len( cChunk ) == 0 ; EXIT ; ENDIF
      nDrained += Len( cChunk )
      IF Len( cChunk ) < nChunk ; EXIT ; ENDIF   // partial → peer stalled
   ENDDO
RETURN nDrained
```

### `ReadBody()` — drain + close on oversize

`src/hix_request.prg` — the `nLen > HIX_MAX_BODY_SIZE` branch now:

```harbour
IF nLen > HIX_MAX_BODY_SIZE
   lw( _( "REQ_BODY_TOO_LARGE", hb_ntos( nLen ) ) )
   ::oIO:Drain( nLen - Len( ::cBodyPre ) )
   ::lKeepAlive := .F.
   ::cBody      := ""
   RETURN ::cBody
ENDIF
```

`cBodyPre` are the bytes pre-read alongside the headers — subtract
them from what still needs draining.

### `HIX_MwBodyLimit` — drain + close before 413

`src/mw/hix_mw_bodylimit.prg` — same treatment before returning
`413 Payload Too Large`:

```harbour
IF nLen > nMax
   oCtx:oReq:oIO:Drain( nLen - Len( oCtx:oReq:cBodyPre ) )
   oCtx:oReq:lKeepAlive := .F.
   oCtx:oReq:Respond( hb_jsonEncode( { "error" => _( 'ERR_PAYLOAD_TOO_LARGE' ) } ), 413, "json" )
   oCtx:lHandled := .T.
   RETURN .F.
ENDIF
```

## Diagnosis trail (why localhost and mobile masked the bug)

- **Localhost**: loopback delivery is effectively atomic per `send()` —
  the entire 5 MB body lands in the receiver's kernel buffer before
  HIX's single `recv()` runs, so one call filled the buffer.
- **Mobile**: worked by luck (timing / MTU) or the client didn't
  surface the truncated `received` as a visible error.
- **Desktop over Cloudflare Tunnel**: within the first 3 ms of the
  request only ~485 KB had traversed browser → CF edge → cloudflared
  → HIX. Single `recv` returned that partial buffer. HIX responded
  early. Deadlock.

The over-limit probe (12 MB body against a 10 MB cap) reproduced a
similar deadlock at the reject path — same root cause, different
branch of the same file.

## Impact

- `HIX_SUBVERSION_SERVER` bumps to `.05`.
- Fully additive on the public surface:
  - `THixIO:Read()` signature unchanged; behavior now honors the
    documented "read `nBytes`" contract. Existing callers that
    already handled short reads continue to work.
  - `THixIO:Drain()` is a new method — additive.
  - `ReadBody()` / `_HixMwBodyLimitRun` internals only; no API
    change.
- WebSocket payloads > MTU are now delivered whole in one
  `oIO:Read( nPayloadLen, ... )` call — a latent bug that would
  have surfaced under fragmentation.
- Behavior visible to clients:
  - Uploads of any size up to `HIX_MAX_BODY_SIZE` complete
    correctly over Cloudflare / nginx / any HTTP proxy.
  - Requests that exceed the cap now get a real 200/413 response
    (depending on route/MW) instead of a hung `fetch()`; the
    connection is closed after the response so the upstream proxy
    aborts the in-flight upload cleanly.
- No changes in public signatures or existing returns.
- Out of scope:
  - **`Transfer-Encoding: chunked` request bodies**. Cloudflare
    Tunnel forwards with `Content-Length` in practice, so this
    was not needed for the deployment that triggered the fix.
    Chunked request support is still a TODO for HIX to be strictly
    RFC 7230-compliant with all upstreams.
