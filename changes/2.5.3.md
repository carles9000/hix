# HIX v2.5.3

**Date:** 2026-11-22
**Base:** v2.5.2
**Plan:** `.claude/plans/2026-11-22_0721 claim2_sqlite_transaction_isolation.md`
**Origin:** Claim 2 del informe de revisión externa v2.5.

**Type:** Transaction isolation fix — el singleton `WDO_Sqlite3`
serializaba *operaciones* con mutex pero **no mantenía el lock entre
`BeginTrans()` y `Commit()`**. Dos handlers concurrentes podían
interleavar `Exec/Query` dentro de la misma transacción lógica,
rompiendo el aislamiento que SQLite documenta ([sqlite.org/isolation](https://www.sqlite.org/isolation.html)).

## TL;DR

Nueva opción `pool_size` en la configuración SQLite3. Default `1`
preserva el comportamiento histórico (singleton). `> 1` activa un
pool real de N conexiones contra el mismo fichero, con reserva por
request — igual que PG/MySQL:

```json
"databases": {
   "APP": {
      "driver":          "sqlite3",
      "file":            "www/data/app.db",
      "journal_mode":    "WAL",
      "busy_timeout_ms": 5000,
      "pool_size":       4
   }
}
```

En apps HIX multi-worker con escrituras concurrentes, pasar de
`pool_size: 1` a `pool_size: 4` es suficiente para que las
transacciones queden aisladas entre hilos. El dispatcher libera la
conexión al final de cada request vía `WDO_ReleaseAllThread()`.

## Cambios

### `src/wdo/sqlite3/wdo_sqlite3.prg`

- Nuevas STATICs `s_hSharedLibs := {=>}` + `s_mtxLib` para refcount
  compartido de la DLL. Un pool con N conexiones ejecuta `LoadLibrary`
  **una sola vez**; las N-1 restantes reutilizan el `pLib` y
  decrementan el contador en `Close()`. `HB_LibFree` sólo corre
  cuando el refcount llega a 0.
- `METHOD Open()` sustituye `::pLib := hb_LibLoad( cDll )` por
  `_WdoSqlite3AcquireLib( cDll )`. Los tres paths de error también
  pasan por `_WdoSqlite3ReleaseLib`.
- `METHOD Close()` libera la DLL vía `_WdoSqlite3ReleaseLib`
  (idempotente, respeta el refcount).
- Helpers `STATIC FUNCTION _WdoSqlite3AcquireLib( cDll )` y
  `_WdoSqlite3ReleaseLib( pLib, cDll )` — claves hash en lower-case
  por si un consumidor pasa el path con diferente casing que otro.

### `src/wdo/sqlite3/wdo_sqlite3_pool.prg`

- `WDO_InitSqlite3Ex()` lee tres claves nuevas del hash:
  - `pool_size` (default `1`),
  - `timeout_ms` (default `5000`, solo `pool_size > 1`),
  - `ping`      (default `.F.`, solo `pool_size > 1`).
- Si `pool_size == 1` → rama singleton legacy (back-compat total).
- Si `pool_size > 1`:
  - Construye factory codeblock `_WdoSqlite3PoolNew` que abre una
    conexión con los parámetros efectivos y el `cPoolKey` seteado.
  - Crea `WDO_Pool():New( cKey, nPoolSize, nTimeoutMs, lPing, bFactory )`
    y hace `Init()` eager de todas las conexiones.
  - Registra el pool vía `WDO_RegisterPool( cKey, oPool )`.
- Guarda contra `:memory:` + `pool_size > 1`: cada `New()` abriría una
  BD privada en memoria (los threads **no** comparten). El driver
  fuerza singleton y emite un `HIX_Dbg` de aviso.
- SQLCipher: la factory serializa el `Open()` de cada conexión; todas
  reciben el mismo `PRAGMA key` sin colisión. La DLL se carga una
  sola vez (ver cambio anterior).
- `WDO_EndSqlite3()` ahora detecta si la key está registrada como pool
  (`WDO_PoolStats`) y dispatcha a `WDO_UnregisterPool` o
  `WDO_UnregisterConn`.

### `tests/wdo/sqlite3/test_wdo_sqlite3.prg`

- **26** `_TestIsolationSurvivesRollback`: hilo A hace `BEGIN; INSERT;
  ROLLBACK`, hilo B hace `BEGIN; INSERT; COMMIT` en paralelo. Con
  pool, el INSERT de B sobrevive al rollback de A. En master (singleton)
  fallaría porque `::lInTrans` del singleton estaría a `.T.` cuando B
  entra.
- **27** `_TestIsolationConcurrentCommits`: dos hilos hacen
  `Transaction({| o | o:Exec("INSERT ...") })` simultáneos. Ambos
  deben retornar `.T.` y las dos filas deben estar en la tabla.
- **28** `_TestIsolationHighConcurrency`: 8 hilos × 5
  `Transaction()` cada uno sobre la misma tabla → 40 inserts
  committed sin `SQLITE_BUSY` (con `busy_timeout_ms: 5000`).
- **29** `_TestIsolationDirtyReadPrevented`: hilo A abre
  `BEGIN; INSERT; <sleep>; COMMIT`; hilo B lee con `SELECT count(*)`
  durante el sleep. En pool, B no ve el INSERT no-commitado de A.
- Helper `_AsNum( x )` — `Fetch_Assoc` sobre `COUNT(*)` devuelve
  numérico, `Val()` sobre numérico lanza "Argument error". El helper
  acepta ambos tipos.
- Suite completa: **70 total | 70 passed | 0 failed**.

## Migración desde v2.5.0 / v2.5.1 / v2.5.2

**Ninguna acción requerida** si tu app no sufre contención. Default
`pool_size: 1` preserva el comportamiento histórico (singleton).

Para apps HIX multi-worker con escrituras concurrentes, recomendado:

```diff
 "databases": {
    "APP": {
       "driver":          "sqlite3",
       "file":            "www/data/app.db",
       "journal_mode":    "WAL",
       "busy_timeout_ms": 5000,
+      "pool_size":       4
    }
 }
```

Regla práctica: `pool_size` ≈ número de workers HTTP que pueden tocar
la BD simultáneamente. Subir por encima de 8 raramente ayuda — SQLite
igualmente serializa writes a nivel de fichero.

## Fuera de scope

- No tocamos PG / MySQL — ya tienen pool real.
- No cambiamos los PRAGMAs activos (WAL, busy_timeout, synchronous)
  ni el formato del fichero SQLite.
- No implementamos savepoints (`SAVEPOINT`/`RELEASE`) — queda fuera
  del contrato actual del driver.
- No modificamos `Rekey()` ni `GetCipherInfo()` — los asserts T13-T16
  del contrato Claim 1 siguen pasando intactos.
- Claim 3 (HTTP framing strict) queda para una release posterior.
