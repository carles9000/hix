# HIX v2.1.01

**Date:** 2026-09-07
**Commit:** `42c592d` — fix(ws): promote WS upgrade behind Cloudflare / reverse proxies

## What was achieved

The WebSocket disconnect (close 1006) has been resolved when the HIX server
sits behind a reverse proxy (Cloudflare, nginx) that inflates the headers
of the initial request. The failure had two chained causes and both have
been fixed.

## Changes

### 1. Protocol detector — wider peek window

Before, the detector read only the first **512 B** with a **10 ms** timeout.
When Cloudflare adds large `CF-*`, `X-Forwarded-*` and `Cookie` headers, the
`Upgrade: websocket` line falls outside that window and the detector
classifies the connection as plain HTTP. With a very short RTT to the
origin, on top of that, the first packet sometimes had not arrived yet.

New defaults in `src/hix_config_data.prg`:

| Parameter          | Before | Now  |
|--------------------|--------|------|
| `peek_bytes`       | 512    | 2048 |
| `peek_timeout_ms`  | 10     | 150  |

### 2. HTTP worker fallback — WS promotion also on plain TCP

`src/hix_worker_http.prg` already promoted to WebSocket upgrade as a
fallback, but only if the connection was SSL. It now does it **also on
plain TCP**, catching the residual cases where the detector still
returns HTTP.

## Regression test

New test `tests/unit/src/hix_test_ws_detector.prg` (Transport group) that
feeds the **same** synthetic Cloudflare request to `HIX_DetectProtocol`
with both configurations:

- `peek_bytes = 512`  → returns HTTP (reproduces the bug)
- `peek_bytes = 2048` → returns WS (validates the fix)

It also covers plain WS, `Upgrade` with mixed-case, plain HTTP and empty peek.

## Impact

- `HIX_SUBVERSION_SERVER` bumps to `.01`.
- No API changes. Projects that already worked keep working the same; the
  ones that were failing behind Cloudflare/nginx now complete the handshake.
