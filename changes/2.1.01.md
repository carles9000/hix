# HIX v2.1.01

**Fecha:** 2026-09-07
**Commit:** `42c592d` — fix(ws): promote WS upgrade behind Cloudflare / reverse proxies

## Qué se ha conseguido

Se ha resuelto la desconexión de WebSockets (close 1006) cuando el servidor
HIX está detrás de un proxy inverso (Cloudflare, nginx) que infla las
cabeceras del request inicial. El fallo tenía dos causas encadenadas y se
han corregido las dos.

## Cambios

### 1. Detector de protocolo — ventana de peek más amplia

Antes el detector leía solo los primeros **512 B** con un timeout de **10 ms**.
Cuando Cloudflare añade `CF-*`, `X-Forwarded-*` y `Cookie` grandes, la línea
`Upgrade: websocket` cae fuera de esa ventana y el detector clasifica la
conexión como HTTP normal. Con RTT muy corto al origen, además, el primer
paquete a veces todavía no había llegado.

Nuevos defaults en `src/hix_config_data.prg`:

| Parámetro          | Antes | Ahora |
|--------------------|-------|-------|
| `peek_bytes`       | 512   | 2048  |
| `peek_timeout_ms`  | 10    | 150   |

### 2. Fallback del worker HTTP — promoción a WS también en TCP plano

`src/hix_worker_http.prg` ya promocionaba a upgrade WebSocket como fallback,
pero solo si la conexión era SSL. Ahora lo hace **también en TCP plano**,
capturando los casos residuales en los que el detector aún devuelve HTTP.

## Test de regresión

Nuevo test `tests/unit/src/hix_test_ws_detector.prg` (grupo Transport) que
alimenta el **mismo** request sintético de Cloudflare a `HIX_DetectProtocol`
con las dos configuraciones:

- `peek_bytes = 512`  → devuelve HTTP (reproduce el bug)
- `peek_bytes = 2048` → devuelve WS (valida el fix)

Cubre también WS plano, `Upgrade` con mixed-case, HTTP plano y peek vacío.

## Impacto

- `HIX_SUBVERSION_SERVER` sube a `.01`.
- Sin cambios de API. Los proyectos que ya funcionaban siguen igual; los
  que fallaban tras Cloudflare/nginx ahora completan el handshake.
