## Fix 1 — Session loader honra `crypt / prefix / seed / gc_days`

### Causa

`src/hix_mw_loader.prg:_MwApplySession` llamaba a `HIX_MwSessionSetup()` con
4 argumentos. La función acepta 9. Las claves `session.prefix`, `session.crypt`,
`session.seed` y `session.gc_days` del `hix.json` se parseaban en el loader
pero jamás llegaban al setup. **`"crypt": true` era un no-op** — los payloads
de sesión quedaban en claro en disco aunque el operador pidiera cifrado.

### Fix

`_MwApplySession` ahora lee las 4 claves vía `UConfig("session", …)` y las
pasa al setup junto con `paths.session`:

```harbour
cPrefix := UConfig( "session", "prefix",  "" )
cSeed   := UConfig( "session", "seed",    "" )
lCrypt  := ( UConfig( "session", "crypt", .F. ) == .T. )
nGcDays := UConfig( "session", "gc_days", 0 )
IF Empty( cPrefix ) ; cPrefix := NIL ; ENDIF   // "" no pisa el default
IF Empty( cSeed   ) ; cSeed   := NIL ; ENDIF
HIX_MwSessionSetup( cCookie, nTtl, nMax, cStorage, cPath, cPrefix, lCrypt, cSeed, nGcDays )
```

`HIX_MwSessionConfig()` expuesta con 5 campos nuevos (`prefix`, `crypt`,
`seed_set`, `gc_days`, `path`) para tests y diagnóstico.

### Tests

`tests/unit/src/hix_test_loader_session.prg` — 3 casos:

* **A**: todos los campos propagan (prefix, crypt=true, seed no vacío, gc_days).
* **B**: `prefix=""` en `hix.json` preserva el valor anterior (semántica NIL).
* **C**: `crypt=false` explícito propaga (inverso de A).

## Fix 2 — `UParam()` fallback a querystring

### Causa

`UParam(cKey)` leía sólo de `oReq:hParam` (route params `:var`). Si el
controller esperaba `UParam("page")` y la URL era `/grid?page=5` (no
`/grid/:page`), devolvía NIL. En el fork esto rompía paginación y search
de grids: todos los parámetros `GET` eran invisibles.

### Fix

Fallback dentro de `UParam()`: si la clave no está en `hParam`, consulta
`QueryParamsAll()`. Prioridad: route params > querystring.

```harbour
IF o != NIL
   HB_HCaseMatch( o:hParam, .F. )
   IF hb_HHasKey( o:hParam, cKey ) ; RETURN o:hParam[ cKey ] ; ENDIF
   hCopy := o:QueryParamsAll()
   IF hb_IsHash( hCopy )
      HB_HCaseMatch( hCopy, .F. )
      IF hb_HHasKey( hCopy, cKey ) ; RETURN hCopy[ cKey ] ; ENDIF
   ENDIF
ENDIF
```

### Tests

`tests/unit/src/hix_test_helpers.prg` — 4 asserts tras los existentes de
`UParam`: fallback a `page=5`, fallback a `sort=name`, default cuando falta,
prioridad `route > querystring`.

## Fix 3 — Scheme desde transporte (cookie `Secure` sobre TLS directo)

### Causa

`THixRequest:Read()` sólo pobló `::cProtoScheme` desde `Forwarded /
X-Forwarded-Proto`. Un request HTTPS directo (sin proxy) dejaba el campo
vacío, y `HIX_SetCookie()` **nunca emitía el flag `Secure`** — las cookies
de sesión viajaban susceptibles de fuga sobre un fallback plain opportunista.

**PENTEST-REPORT §4.**

### Fix

Semilla `::cProtoScheme := iif( oIO != NIL .AND. oIO:lUseSSL, "https", "http" )`
antes del bloque de proxy. `X-Forwarded-Proto` sólo pisa cuando es no vacío.
La rama RFC 7239 Forwarded ya usaba `hb_HHasKey`, sin cambio.

### Tests

`tests/unit/src/hix_test_proxied.prg` + `TMockIO.lUseSSL` nueva data — 5 asserts:

* Plain TCP seeds `http`.
* TLS directo seeds `https` (**regresión principal**).
* `X-Forwarded-Proto` pisa el seed.
* Proxy sin XFP preserva el seed TLS.
* `Scheme()` wrapper devuelve `http`/`https`.

## Fix 4 — Precedencia `HIX_KeySet > config.json > generated`

### Causa

El comentario original de `HIX_KeysLoadFromAppConfig()` lo decía textualmente:
*"Values already set by HIX_KeySet are overwritten — bootstrap runs before
user code by design."* Inverso al principio least-trust: un bootstrap que
hiciera `HIX_KeySet("csrf", getenv("HIX_CSRF_KEY"))` quedaba pisado por un
default publicado en `config.json`. Y cuando faltaba una clave en
`config.json` no se generaba nada — el slot quedaba vacío y los engines
caían a defaults builtin sin aviso.

### Fix

Precedencia invertida + generación en memoria como último recurso para los
5 slots core (`csrf, jwt, session, token, resource`):

1. `HIX_KeySet()` — autoridad máxima (env vars, fichero fuera del docroot).
2. `config.json > "keys"` — sólo si el slot está vacío.
3. Auto-generado por `_HixGenKey()` (misma entropía que
   `_HixGenRandKey` original) — con WARN explicando que los tokens mueren
   con el proceso.

Pattern `H!x@` sigue levantando WARNING `SECURITY:` cuando se detecta.

### Tests

`tests/unit/src/hix_test_keys.prg` — 7 asserts T18-T24: `HIX_KeySet` gana
sobre config, `config.json` rellena slots no seteados, auto-generación,
claves generadas difieren, no persisten entre resets, `HIX_KeySet("")` cede
a config.

## Fix 5 — `www/config.json` deja de ser almacén de secretos

### Causa

`HIX_ConfigAppDefaults()` generaba 5 claves aleatorias y `HIX_ConfigAppSave()`
las persistía en `www/config.json`. v2.4.1 cerró el acceso HTTP vía
dispatcher ACL (`12a5eb3`), pero el fichero en disco **seguía conteniendo
los secretos**. Vectores restantes de fuga:

* `git add www/config.json` por error → claves en el history.
* Backup/deploy: `tar/zip` del docroot incluye los secretos.
* Otros procesos locales en el host pueden leer el fichero.
* Modo clásico (sin hixstyle): el ACL del dispatcher no aplica y
  `/config.json` vuelve a ser descargable.

**PENTEST-REPORT §1** (vector de disco complementario al §1 de v2.4.1).

### Fix

Borrado el bloque `hDef[ "keys" ]` de `HIX_ConfigAppDefaults()` y la helper
huérfana `_HixGenRandKey()` (equivalente vivo en `hix_keys.prg` como
`_HixGenKey()`). Comentario largo documentando el nuevo flujo.

### Tests

`_AudA0116_RandomDefaults` migrado: ahora asserta que (a) `HIX_ConfigAppDefaults()`
no incluye la sección `keys` y (b) la aleatoriedad por run se verifica
contra `HIX_KeysLoadFromAppConfig()` en vez de contra los defaults.

## Fix 6 — CSRF tokens ligados a la sesión

### Causa

`HIX_CsrfMakeToken()` firmaba un payload aleatorio sin ligar a sesión.
`HIX_MwCsrfCheck()` validaba sólo la firma HMAC. Vector de ataque:

1. Atacante abre página pública (sin login) → recibe un token CSRF válido.
2. Lo inyecta en un form dirigido a la víctima (ya logada).
3. El form POST pasa validación: la firma es correcta, nadie comprueba
   a qué sesión pertenece el token.

**PENTEST-REPORT §N-01.** (`HIX_MwCsrf`, la variante que guarda el token en
sesión, no era vulnerable: comparaba contra el token almacenado en la
propia sesión.)

### Fix

* `HIX_CsrfMakeToken(cData)`: cuando `cData` se omite, el payload por
  defecto es el SID activo (vía `oReq:hData._ctx` o `HIX_GetContext()`
  thread-local). Sin sesión activa, fallback al random seed histórico
  — los flows stateless (public forms) siguen funcionando.
* `HIX_CsrfBound(cToken)` **(nueva)**: `.T.` cuando el cData embebido
  en el token coincide con el SID actual. `.T.` (skip) sin sesión.
  `.F.` sólo cuando hay sesión y el token fue minteado para otra.
* `HIX_MwCsrfCheck()`: predicate de rechazo amplía con
  `.OR. ! HIX_CsrfBound(cGot)`.

### Tests

`tests/unit/src/hix_test_csrf.prg` — 6 asserts T23-T28: skip stateless,
accept same-session, **reject cross-session (regresión CVE)**, payload sin
`|`, token sin `.`, forged payload+firma de origen distinto.

## Breaking changes

**4 cambios de comportamiento visibles al operador.** Documentar antes de
desplegar.

### 1. Session store cifrado cuando `crypt: true`

El flag ya hace lo que dice. Sesiones viejas escritas en claro con
`crypt=true` en `hix.json` serán ilegibles tras el upgrade. Mitigación:
flush del directorio `paths.session` en el deploy, o degradar a
`crypt: false` si no se cambia la seed.

### 2. Cookie `Secure` forzada en TLS directo

Un servidor HIX arrancado con cert TLS pero accedido sin HTTPS (ej. desde
`http://localhost` con cert selfsigned) deja de recibir cookies de sesión
porque el browser las rechaza (`Secure` + `http` = drop). Mitigación: usar
HTTPS siempre que el servidor tenga `oIO:lUseSSL = .T.`.

### 3. `config.json` deja de minting claves

Primer arranque de una app nueva **ya no escribe** la sección `keys` en
`www/config.json`. El operador debe:

* **Opción A (recomendada)**: `HIX_KeySet()` en `Main()` leyendo de env
  vars o un fichero fuera del docroot (`/etc/hix/keys.env`, `.env` con
  `chmod 600`, etc.).
* **Opción B (legacy)**: añadir manualmente `"keys": { … }` a
  `www/config.json` — se respeta pero sigue siendo vector de fuga por
  disco.
* **Opción C (sin acción)**: HIX genera claves en memoria y emite WARN.
  **Todos los tokens/sesiones mueren en cada restart**.

### 4. CSRF tokens ligados a sesión

Forms minteados en una ruta anónima (pre-login) y enviados a una ruta
autenticada (post-login) son rechazados — el token no está ligado a la
sesión que lo validará. Mitigación: mintear tokens dentro del flow
autenticado, no antes.

Apps que siempre mintean el token dentro de la sesión autenticada
(mayoría) no notan nada.

### 5. Hixstyle ACL — blacklist por extensión + autoridad folder

Con `aAllowDirs != NIL` (hixstyle activo) se añaden tres cambios en
`src/hix_dispatcher.prg`:

* **Blacklist de extensiones**: `.dbf, .cdx, .fpt, .dbt, .ntx, .hbp,
  .hbx, .hbs, .hbm, .hbc, .hbt, .ch, .hbh, .bak, .swp, .tmp, .old, .pem,
  .key, .crt, .cer, .pfx, .p12` → 403 directo aunque la carpeta esté en
  whitelist. Cubre fuga de data files (`.dbf`), fuentes (`.hbp`), y
  material criptográfico (`.pem`).
* **Dotfile deny**: cualquier segmento del path que empiece por `.`
  (fichero oculto o directorio) devuelve 403. Cubre `/public/.env`,
  `/public/.htaccess`, `/public/.git/config`, `/.gitignore`.
* **Autoridad folder sobre `lExecPrg`**: en hixstyle, el flag `exec` del
  `AllowDir(dir, lExec)` manda sobre el `lExecPrg` global. Antes, con
  `lExecPrg=.T.` (default) y `AllowDir("public", .F.)`, un
  `/public/app.prg` **ejecutaba**. Ahora 403.

Breaking para apps que servían legítimamente alguna de esas extensiones
dentro del docroot con hixstyle — raro pero posible. Mitigación:
registrar una ruta explícita vía `HIX_FileRoute` (bypassa la ACL) o
mover el fichero fuera del docroot y servirlo por controller.
